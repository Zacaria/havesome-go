Une architecture qui suit le métier.

Pour une commande de réservation : le transport traduit la requête, le cas d’usage orchestre, le domaine protège ses règles. L’infrastructure satisfait les ports.

Un module, des responsabilités

reservation/
├── go.mod
├── cmd/api/main.go          # composition HTTP
├── cmd/reserver/main.go     # composition CLI
└── internal/
    ├── domain/              # réservation, règles
    ├── application/         # cas d’usage, ports
    ├── transport/http/      # handlers, DTO
    └── infrastructure/      # stockage, adaptateurs

La direction des dépendances

Le handler appelle application.Reserver. Le cas d’usage manipule domain.Reservation et dépend d’une interface de dépôt définie à sa frontière. L’adaptateur SQL implémente ce port ; cmd/api assemble les composants. Le domaine ne connaît ni HTTP ni SQL.

Ce découpage est un exemple, pas une convention imposée par Go. Un petit programme peut rester dans un seul package ; créez une frontière lorsqu’elle protège une règle ou facilite un changement.

Modules et versions

go.mod déclare le module et ses exigences ; go.sum vérifie les empreintes de contenu des modules téléchargés. go mod tidy ajuste les exigences et sommes selon les packages utilisés. Relisez ses changements dans la même revue que le code.

La sélection minimale des versions retient, pour un chemin de module, la plus haute version minimale requise dans le graphe. Une mise à jour peut donc modifier des dépendances transitives ; vérifiez le graphe et les tests.

TDD : rouge → vert → améliorer

Écrivez un cas métier qui échoue, vérifiez son échec, implémentez le minimum puis améliorez le code sans changer le comportement. testing suffit pour démarrer ; tables de cas, httptest, fuzzing et -race répondent à des risques différents.

Une API HTTP peut utiliser net/http ; une CLI peut démarrer avec flag. Ajoutez une bibliothèque quand elle retire une complexité réelle.

01 / LE POINT DE DÉPART

La simplicité est une contrainte de conception.

Go ne cherche pas à offrir toutes les façons d’exprimer une idée. Il cherche à rendre les programmes compréhensibles par une équipe, longtemps après leur écriture.

Approfondir ce chapitre

La compilation produit des exécutables natifs ; un ramasse-miettes gère la mémoire des objets accessibles et le runtime ordonnance les goroutines. Le langage est statiquement typé, mais l’inférence locale évite de répéter des types évidents. La bibliothèque standard fournit notamment HTTP, JSON, TLS, tests et profilage.

Cette simplicité n’élimine ni la conception ni les compromis. Un binaire n’est pas automatiquement portable entre systèmes ou architectures ; CGO et des ressources externes peuvent ajouter des dépendances. Le garbage collector réduit la gestion manuelle, sans supprimer le coût des allocations ni les besoins de mesurer.

Le bon réflexe

Commencez par une solution explicite et mesurez avant d’optimiser. Une abstraction se justifie par le problème qu’elle retire, pas par le nombre de couches qu’elle ajoute.

02 / LE MODÈLE

Des valeurs, des méthodes et de petites interfaces.

Lire un programme Go

Un fichier commence par package, puis ses imports. Les fichiers d’un même répertoire forment normalement un package ; le package exécutable main fournit une fonction main. Déclarez une variable avec var n int ou, dans une fonction, n := 3 lorsque le type est évident. const définit une constante ; une variable déclarée mais inutilisée dans une fonction est une erreur de compilation.

if peut introduire une variable locale avant sa condition. for est la seule construction de boucle ; range parcourt notamment tableaux, slices, maps et chaînes. Attention : parcourir une chaîne avec range produit des positions en octets et des runes Unicode, pas nécessairement des caractères visibles. switch ne passe pas au cas suivant automatiquement. defer programme un appel à la sortie de la fonction, en ordre inverse des déclarations ; ses arguments sont évalués au moment du defer. Utilisez-le pour libérer une ressource acquise, mais tenez compte des erreurs de fermeture quand elles comptent.

Un tableau [3]int inclut sa longueur dans son type et se copie comme valeur. Une slice []int décrit une fenêtre sur un tableau ; len donne la longueur visible et cap la capacité depuis son début. append renvoie une nouvelle slice : réaffectez son résultat. Il peut réutiliser le tableau partagé ou en allouer un autre ; ne dépendez pas de l’un ou de l’autre pour isoler les modifications. Utilisez copy pour copier explicitement les éléments.

Une variable contient une valeur. L’affectation et le passage à une fonction copient cette valeur : pour une structure, ses champs sont copiés ; pour une slice, c’est son descripteur qui est copié, pas le tableau sous-jacent. Deux slices peuvent donc partager leurs éléments. Une map est également une valeur de référence vers une structure partagée ; les accès concurrents nécessitent une coordination.

Les types ont une valeur zéro : 0, false, chaîne vide, ou nil selon le type. Une slice nil peut recevoir un append, contrairement à une map nil qui doit être initialisée avant écriture. Pensez à la différence entre « vide » et « absent » lorsque votre protocole la rend significative.

type Compteur struct { N int }

func (c *Compteur) Incr() { c.N++ }

func exemple() int {
    c := Compteur{} // valeur zéro utilisable
    c.Incr()
    return c.N
}

Une interface ordinaire décrit un ensemble de méthodes ; un type la satisfait implicitement. Les interfaces générales peuvent aussi décrire des ensembles de types par des termes et des unions ; les interfaces non basiques ne s’utilisent pas comme types de valeurs ordinaires. Attention à l’interface nil : une interface qui contient un pointeur nil typé n’est elle-même pas nil, car son type dynamique est présent. Une interface vit souvent près du code qui en a besoin. Une fonction qui lit accepte par exemple io.Reader plutôt qu’un client concret. Ne créez pas une interface pour chaque structure : attendez un besoin réel de substitution ou de frontière.

L’embarquement de types favorise la composition, pas un héritage de classes. Une méthode à récepteur pointeur peut modifier le récepteur ; une méthode à valeur travaille sur une copie. Choisissez aussi en fonction de la cohérence de l’ensemble de méthodes et évitez de copier une structure contenant un mutex déjà utilisé.

Les paramètres de type conviennent lorsque le même algorithme s’applique à plusieurs types et que les contraintes expriment ce qu’il utilise. Ils ne remplacent pas systématiquement les interfaces. Go 1.27 introduit notamment les méthodes génériques : vérifiez la version minimale du module avant de les employer.

03 / LES FRONTIÈRES

Une erreur fait partie du résultat.

La convention Go retourne une erreur explicite, généralement en dernière position. Traitez-la à l’endroit où vous pouvez agir ; sinon ajoutez du contexte et transmettez-la. Ne la journalisez pas à chaque niveau : le propriétaire de la requête ou du travail décide souvent de la réponse et du log.

Approfondir ce chapitre
Approfondir ce chapitre
func charge(r io.Reader) ([]byte, error) {
    data, err := io.ReadAll(r)
    if err != nil {
        return nil, fmt.Errorf("lire la réponse : %w", err)
    }
    return data, nil
}

%w conserve la chaîne d’erreurs ; errors.Is et errors.As permettent de l’inspecter sans comparer des messages. Exposer une erreur interne à travers une API crée toutefois un contrat : ne l’enveloppez avec %w que si l’appelant doit pouvoir en dépendre. panic n’est pas le mécanisme ordinaire des erreurs attendues.

Une API HTTP doit aussi limiter les entrées, fermer les corps et attribuer des délais aux opérations réseau. Un contexte porte annulation et échéance entre appels ; il n’interrompt que les opérations qui l’observent. Évitez d’y cacher des dépendances métier et appelez la fonction d’annulation retournée par context.WithTimeout.

Une frontière HTTP peut rester une fonction. Ici http.HandlerFunc adapte une fonction au serveur ; le test utilise un enregistreur, sans ouvrir de port. L’exemple ne prétend pas gérer une entrée métier ou l’authentification.

func bonjour(w http.ResponseWriter, r *http.Request) {
    if r.Method != http.MethodGet {
        w.Header().Set("Allow", http.MethodGet)
        http.Error(w, "méthode non autorisée", http.StatusMethodNotAllowed)
        return
    }
    w.Header().Set("Content-Type", "text/plain; charset=utf-8")
    fmt.Fprint(w, "bonjour")
}

Le test de cette fonction utilise httptest pour vérifier la réponse sans serveur réseau. Ici, chaque cas précise son attendu ; ajoutez des cas selon le contrat de votre handler.

func TestBonjour(t *testing.T) {
    for _, tc := range []struct{ method string; status int; body string }{
        {http.MethodGet, http.StatusOK, "bonjour"},
        {http.MethodPost, http.StatusMethodNotAllowed, "méthode non autorisée\n"},
    } {
        t.Run(tc.method, func(t *testing.T) {
            w := httptest.NewRecorder()
            http.HandlerFunc(bonjour).ServeHTTP(w, httptest.NewRequest(tc.method, "/", nil))
            if tc.method == http.MethodPost && w.Header().Get("Allow") != "GET" {
                t.Fatalf("Allow = %q", w.Header().Get("Allow"))
            }
            if w.Code != tc.status || w.Body.String() != tc.body {
                t.Fatalf("got %d %q", w.Code, w.Body.String())
            }
        })
    }
}

04 / LE TEMPS

Démarrer une goroutine est facile. Savoir quand elle s’arrête est essentiel.

Une goroutine est une unité d’exécution concurrente gérée par le runtime. La concurrence structure des tâches qui se chevauchent ; elle ne garantit ni parallélisme, ni accélération. Un canal permet de communiquer et de synchroniser ; un mutex peut être plus simple pour protéger un état partagé. Ni l’un ni l’autre ne remplace une politique de propriété des données.

Approfondir ce chapitre
func attendre(ctx context.Context, travail <-chan string) (string, error) {
    select {
    case v, ok := <-travail:
        if !ok { return "", io.EOF }
        return v, nil
    case <-ctx.Done():
        return "", ctx.Err()
    }
}

Pour chaque goroutine, identifiez qui la lance, qui attend son résultat, ce qui la débloque et ce qui se passe à l’annulation. Un canal non bufferisé attend un partenaire ; un buffer ne résout pas à lui seul une fuite. Seul le producteur qui sait qu’aucun autre envoi n’aura lieu ferme normalement le canal. Si plusieurs cas de select sont prêts, ne supposez pas que l’annulation sera toujours choisie.

Le détecteur de races observe les exécutions réellement parcourues : go test -race ./... augmente la confiance mais ne prouve pas l’absence de races dans les chemins non exercés. Les invariants métier et la terminaison demandent leurs propres tests.

05 / LA BOUCLE DE TRAVAIL

Le langage vient avec sa boîte à outils.

Un module décrit son chemin, sa version minimale de Go et ses dépendances dans go.mod ; go.sum enregistre des empreintes. Un dépôt contient souvent un module, mais ce n’est pas une obligation. Les packages organisent le code et leur chemin d’import fait partie de leur identité. Les noms commençant par une majuscule sont exportés.

Approfondir ce chapitre

gofmt -w .Formater le code.

go test ./...Exécuter les tests des packages.

go test -race ./...Observer les races sur les chemins exécutés.

go vet ./...Détecter certaines constructions suspectes.

go build ./...Compiler les packages.

govulncheck ./...Analyser les vulnérabilités connues avec l’outil installé séparément.

Les tests vivent dans des fichiers _test.go, à côté du code. Les tests en table rendent les cas et leurs noms visibles ; les benchmarks et le fuzzing complètent les exemples ciblés. Un benchmark sans contexte de charge et sans comparaison n’est pas une preuve de performance en production.

Pour trouver une bibliothèque, commencez par la documentation standard et pkg.go.dev, puis examinez maintenance, licence, surface d’API et transitivité. Les outils pprof et trace aident à observer allocations, CPU, blocages et ordonnancement ; protégez leurs endpoints de diagnostic en production.

06 / LE SERVICE RÉEL

Le runtime ne connaît pas vos contraintes métier.

Imaginons une API qui consulte un fournisseur. La requête peut être annulée par son client, ralentir chez le fournisseur ou réussir après un délai trop long. Définissez un budget de temps global ; transmettez le contexte ; limitez la concurrence et la taille des réponses ; fermez le corps de réponse. Une nouvelle tentative ne doit être envisagée que si l’opération est idempotente ou si le destinataire garantit la déduplication d’une clé d’idempotence dans un périmètre et une durée adaptés ; fournir une clé sans cette garantie ne suffit pas.

Approfondir ce chapitre

À l’arrêt, cessez d’accepter de nouvelles requêtes, donnez un délai aux requêtes en cours, puis arrêtez les travailleurs et libérez les ressources. http.Server.Shutdown aide pour HTTP, mais ne gère pas magiquement tous les goroutines et connexions applicatives. Testez aussi les pannes : dépendance lente, annulation, surcharge et arrêt pendant un travail.

Les métriques révèlent tendances et saturation ; les logs structurés expliquent un événement ; les traces relient les appels. Ne placez pas de secrets ni de données personnelles inutiles dans ces signaux. Mesurez le coût réel avant de changer les réglages du ramasse-miettes ou d’introduire des pools.

07 / LE JUGEMENT

De « ça marche » à « on sait pourquoi ça tient ».

La séniorité ne se résume pas à la syntaxe ni à un nombre d’années. Elle se voit dans les questions posées avant et après l’écriture du code. Ces contrastes décrivent des habitudes possibles, pas une étiquette pour les personnes.

La première solution

Lancer une goroutine par élément pour réduire la durée apparente.

Le pas de plus

Définir une limite, un budget, une annulation et observer la saturation du service en aval.

La première solution

Retourner le message d’erreur tel quel au client.

Le pas de plus

Conserver le contexte en interne, classifier l’erreur et exposer une réponse stable sans fuite d’information.

La première solution

Introduire un framework et une interface par composant.

Le pas de plus

Choisir les frontières qui simplifient réellement les changements et les tests ; supprimer les couches inutiles.

La première solution

Considérer les tests verts comme une preuve de sûreté.

Le pas de plus

Nommer ce qui n’est pas couvert : contention, charge, timeouts, sécurité, versions et comportement en panne.

Avant une revue, demandez-vous : qui possède cette ressource ? Quelle opération peut rester bloquée ? Quel contrat l’appelant peut-il observer ? Quel signal montrera que le système se dégrade ? Et quelle preuve pourrait invalider notre hypothèse ?
